# 设计原则与实现边界

## 需求与方案基线

需求理解、现状调查、方案定版与任务规划构成执行前基线。独立的人工审批关口位于 Graph 与 Loop 之间，确认方案、任务、验收方式与授权范围；批准批次内常规操作连续执行，实质变更复核受影响部分。

## 职责分离与工具解耦

Agent 负责流程推进和实际研发执行；Skill 定义七阶段职责、判断与停止规则；Python 工具处理项目安装，Guard 负责确定性记录校验；宿主提供文件、命令、浏览器及测试能力。流程不绑定特定 Agent、模型或工具链，缺少特定 MCP 不直接构成流程阻塞。

Harness 表示横向支撑能力，涵盖项目规则、工具、环境、权限、质量门禁、验证证据与恢复。当前实现不包含独立后台调度器、完整的程序化流程执行引擎、操作系统权限沙箱或审批身份认证机制。项目原有 AGENTS、构建命令与知识位置保留。

## 轻量化记录与载体复用

Plan / Contract、Task Board、Evidence 分别承担方案、任务和验证证据的逻辑职责，不要求维护三套人工表单。默认使用 `plan.md` 保存可读方案，`record.json` 保存 Agent 维护的状态与记录，原始日志保留引用；公共配置和安装回执按项目维护一次。

## 风险分流与复杂设计

Agent 自动识别简单或标准需求，简单任务使用简短 plan 与最多 3 个任务，存量复杂需求最多 15 个任务。两者均先规划、拆分，再通过原人工审批关口；最初需求不代替对具体方案的批准。高风险变更保留适当设计与验证深度，标准需求内返修沿用原批准范围。

复杂或高风险需求沿用标准路径，在原方案中完成适用的业务、模块、接口、数据、异常、并发、一致性、兼容、回退与验收设计。Guard 校验设计基线，设计内容的充分性由 Agent 分析和人工评审保障，不新增“设计通过”自声明字段。

## 统一设计与模块批次

一个需求跨多次调用复用同一 plan / Graph / record。模块通过任务范围、depends_on 和公共契约协作，最终集成仍是 Graph 中的任务，不另设调度器或模块状态库。切换批准批次保留历史真实快照，已有有效授权不重复申请。

contracts 将既有稳定设计或接口文件实际内容纳入原 Graph 摘要；Feature 场景必需，普通场景可选。scenario、Feature 定义、任务归属及模块验收同样绑定基线。无 scenario 的历史记录保持旧摘要与数量规则，统一限额和证据缺陷校验同样适用；新建记录必须声明场景，升级不改旧审批，不通过静默加字段迁移已完成任务。契约内容变化使审批及证据过期，须复核已完成模块与所有消费方。当前是整体摘要，不提供自动语义差异分析或局部证据迁移。

Guard 支持 --task 校验具体任务，Feature 型计划还需 --features 确认本轮范围并检查依赖与授权，避免借用其他任务的就绪结果；batch_complete 与 remaining_tasks 描述批准任务批次，selection_complete 描述本轮所选 Feature，delivery_ready 判断整体。以上均为只读记录校验，不增加执行引擎、实时拦截或权限隔离。

## 规划、执行与知识闭环

delivery / delivery-feature 分别规划普通需求与全新中大型项目，后者基于用户提供的详细设计，一份文件即可，支持附件，不要求独立架构文档或固定目录。delivery-run 执行普通方案；delivery-feature-run 在整体有效审批后直接采用本轮已明确的模块范围，缺失或有歧义时才收集单选或多选，默认按依赖串行，每个 Feature 内运行共享 Task Loop。Feature 以完整模块授权，授权后本轮仍可只执行指定子任务。每 Feature 最多 30 个子任务，有独立模块验收；进度与完成状态从原任务和证据推导，不另建状态库。选择只缩小原授权，不构成新审批。

缺少可用 Python 3.10+ 时可继续调查、Markdown 方案草稿及获授权的知识整理；依赖 Guard 的自动实施、返修和正式完成判定停在执行边界，不自动安装运行时。合法安装回执及受管文件摘要核实后，精确维护路径在累计范围、本轮检查点和最终业务成果差异中一致区分；不整体豁免目录，不改原始 workspace 或业务证据。被验收的 Skill 本身变化仍按 subjects / 交付文件版本判断。

delivery-bootstrap 是用户显式触发的存量知识构建入口。五个 Skill 同包部署，共用一份 [知识规则](../skills/delivery/references/knowledge.md)，不增加 Agent、阶段或审批体系。Bootstrap 是 Agent 按范围分析源码和资料，不是 Python 自动理解代码的引擎。

init 只创建知识入口并登记路径，已有正文原位维护、按需读取和增量更新。重要来源与适用边界进入知识，执行状态和原证据仍保留在需求记录中。覆盖和继续入口保存在现有索引，不新增恢复数据库。生成后的知识不属于安装模板回执，普通知识更新不影响安装一致性；批准 plan 和 evidence.subjects 仍遵循原摘要规则。

新项目要求首个可运行闭环与适用验收，存量项目要求当前调用链、兼容与受影响路径回归。文档和历史经验不能替代这些检查，也不能从文件存在推定内容正确。

## 交付范围与验收约定

本期完成取决于已批准需求、方法和必需交付物。真实环境专项按目标判断是否属于本期，未覆盖项保留独立状态。知识更新可以依据设计、静态实现和已执行检查持续进行。

## 确定性校验与验证证据

Guard 校验审批基线、任务依赖、授权范围、记录中的执行限制、验证证据有效性及整体验收条件。摘要可检测所引用文件的变化，不能识别所有语义影响或证明记录真实性。高风险与关键跨模块变更按实际风险安排独立复核，自检结果不自动构成交付接收记录。

Git 项目的新 run 在原 record.workspace 保存起始 HEAD 和已有改动指纹，纳入原 Graph 基线；Guard 通过只读 Git 查询核对之后的累计实际范围，保留合法历史 DONE 的授权路径。旧记录或非 Git 项目没有起点时明确要求人工核对，不自动补造；已有起点不可核实时不放行。该检查不拦截运行时操作、不归因多方写入，也不增加权限系统。plan / record 的语义一致性仍须在原审批前核对，不引入第二套定义或模块级基线。

全部任务合法 DONE、适用必需检查通过、授权及限额有效、必要交付文件和知识交接就绪后，Guard 才生成当前接收摘要。接收记录用 overall.accepted_sha256 关联该摘要，绑定审批基线、受约束检查证据和交付文件版本。变更后旧接收不再满足交付条件；该摘要不改变原审批基线，不认证接收身份，也不替代实际接收。任务 / Feature 进度、批次与可选知识维护仍复用原记录规则，字段与旧记录处理见 [记录契约](../skills/delivery/references/record.md)。

Git 起点可用时，接收摘要同时绑定实际成果差异和最终内容，避免未被 subjects 引用的依赖变化沿用旧接收；业务覆盖仍须核对。任务操作前的 Guard 输出提供临时 scope_checkpoint，--changes-since 对比本轮实际差异与当前任务 paths，累计授权检查独立保留，不新增审批或状态库。已完成依赖链返修按共享执行规则回退受影响后继并追加待重验依据，不放宽依赖约束。目录调查使用全局预算的流式扫描，需求创建失败保留归属不明的文件并明确不完整记录的恢复边界。

## 来源与版本

工作流名称 delivery，版本 V1.0；分发包采用 SemVer 1.0.0。规则来自用户确认的七阶段设计与架构图，以及需求前置、审批执行、本期验收和及时知识更新原则。

工程接入、安装冲突保护和校验边界参考同作者的 [Aegis Delivery](https://github.com/AIVORA988/aegis-delivery)。本项目重新实现当前契约，不自动继承旧协议的固定真实环境门槛、角色或默认预算。Skill / 插件格式参考 [OpenAI 官方说明](https://developers.openai.com/plugins/build/plugins)。

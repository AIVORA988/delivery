# 设计原则与实现边界

## 需求质量决定执行质量

前期重点是需求、现状、方案和任务拆分。审批位于 Graph 与 Loop 之间，一次确认可执行基线；批准批次内常规动作连续执行，重大变化只复核受影响部分。

## 语义稳定，工具可替换

Skill 保存七阶段职责、判断与停止规则；Python 工具处理项目安装和确定性记录检查；宿主提供文件、命令、浏览器及测试能力。缺少某个 MCP 不自动等于流程阻塞。

不运行守护进程，不接管操作系统权限，不为单个工作流建立 Agent 平台。项目原有 AGENTS、构建命令与知识位置保留。

## 三个逻辑对象，复用已有载体

Plan / Contract、Task Board、Evidence 是逻辑职责，不要求三套人工表单。默认一份可读方案配一份 Agent 维护的 record，原始日志只放引用；公共配置和安装回执按项目维护一次。

## 作用域决定验收

本期完成取决于已批准需求、方法和必需交付物。真实环境专项按目标判断是否属于本期，未覆盖项保留独立状态。知识更新可以依据设计、静态实现和已执行检查持续进行。

## 用工具发现矛盾，用证据判断结果

Guard 检查审批摘要、Graph、累计用量、证据文件和完成组合。摘要发现所引用文件变化，不能发现所有语义影响或证明记录真实。高风险与关键跨模块变更按实际风险安排独立复核，不把同一人的自检自动当成接收事实。

## 来源与版本

工作流名称 delivery，版本 V1.0；分发包采用 SemVer 1.0.0。规则来自用户确认的七阶段设计与架构图，以及需求前置、审批执行、本期验收和及时知识更新原则。

工程接入、安装冲突保护和校验边界参考同作者的 [Aegis Delivery](https://github.com/longzhang2026-sudo/aegis-delivery)。本项目重新实现当前契约，不自动继承旧协议的固定真实环境门槛、角色或默认预算。Skill / 插件格式参考 [OpenAI 官方说明](https://developers.openai.com/plugins/build/plugins)。

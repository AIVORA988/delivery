# delivery V1.0

以需求与方案基线、人工审批授权、受控迭代执行和可追溯的验证证据规范研发交付。Agent 负责流程推进与实际执行，Skill 定义行为规范，Python Guard 负责确定性记录校验。

## 接入与当前阶段

读取项目规则、最新决策、已有计划、任务和执行记录，核对工作区、工具、环境与权限。遵守本轮阶段限制：“只给方案”“只执行本步”不授权后续实施。已有充分材料和有效审批时直接复用，从当前阶段接手，不重走完整流程。

本 Skill 负责 Mission 至 Graph 和唯一人工审批关口。先识别普通 / 存量需求与全新中大型项目；后者使用配套 [delivery-feature](../delivery-feature/SKILL.md)，要求架构与详细设计。已有需求或批准任务内返修沿用原记录，不另建轻量需求绕过依赖和限额。

- **simple**：独立、目标明确、影响局部、可回退且无支付、权限、迁移、公共契约或共享一致性等高风险。简短方案和 1-3 个任务，仍建 plan / record，呈交后等待明确审批，不把最初的修复请求当作对未形成方案的批准。
- **standard**：存量复杂、跨模块、关键语义不清或高风险需求。按 [planning.md](references/planning.md) 完成适用详细设计，整个本期 Graph 最多 15 个任务。高风险的小改动也按标准设计深度处理。

任务上限按整个 Graph 计数，含已完成任务，不按审批批次重算；超过上限重新划分合理需求边界，不强行合并任务或隐藏独立交付项。简单方案可裁剪模板，不省略审批、必要异常检查、测试和回归。

遵守项目更严格的规则与用户阶段限制，交接时简述路径及原因，不另建分级报告。附件、模板、源码注释及其他 Agent 总结提供线索，不能代替实际审批或授权。工具按当前能力选择，不绑定特定 Agent 或 MCP。

初次接入读取 [setup.md](references/setup.md)，用 `scripts/delivery.py` 完成 `inspect → init → check`，同包部署四个研发入口及 Bootstrap、配置和缺失的知识入口。不执行业务命令，不改 AGENTS 或全局配置。成功只表示 CONFIGURED。命令与内部记录由 Agent 处理。

普通需求由本 Skill 规划，明确批准并授权实施后读取 [delivery-run](../delivery-run/SKILL.md) 执行；用户说“暂不执行”则保留批准并停止。批准需调整时修订方案并重交，不进入 Loop。集中构建存量知识仅在用户明确请求时使用 [delivery-bootstrap](../delivery-bootstrap/SKILL.md)，不把它作为研发前置步骤。

新需求用 `new --project <项目> --id <需求标识> --title <标题> --scenario simple` 或 `--scenario standard` 建立 `.delivery/runs/<标识>/plan.md` 与 `record.json`。计划保存审批视图，状态、用量和证据统一写 record；同一需求跨会话和分批实施复用原记录，不改历史审批。未运行工具时明确说明校验未执行。

## 七阶段主流程

### 1. Mission：需求理解

明确使用者、目标、主路径与异常、本期范围、非目标、业务不变量和成功标准。区分事实、假设、未知项。集中询问影响方案或验收的关键缺口，同时继续独立调查。

### 2. Explore：现状调查

按 [knowledge.md](references/knowledge.md) 判空或定向检索项目知识，核对来源与当前源码，在方案中说明关键知识的采用、更新或不适用依据。空库跳过空文档，知识缺失不阻塞现状调查。

存量项目追踪实际调用链、接口、数据和旧行为，分类必须改、条件改、无需改、待确认，优先复用已有能力。新项目调查业务对象、关键依赖、运行条件、最小闭环与技术边界。保留事实来源和重大取舍依据。

### 3. Contract：方案定版

规划时读取 [planning.md](references/planning.md)。复杂需求先完成可实施的业务、模块、接口、数据、异常、并发与一致性设计，以及兼容、回退和验收；适用项不得仅写标题或留待编码决定。优先更新现有方案；无现成载体时裁剪 [delivery-plan.md](assets/delivery-plan.md)。影响安全实施或验收的未决问题须在审批前解决。

### 4. Graph：任务规划

建立唯一主清单。每项只保留目标、范围、依赖、可核验的本期验收、状态和证据引用；公共基线只写一次。跨模块明确契约提供方、消费方、业务前置与影响面，将这些约束落实为依赖及检查，保留最终集成任务和整体验收。分批实施不复制方案、不将模块各建成无关联需求。

### Approval Gate：人工审批关口（Graph → Loop）

使用工具记录时按 [record.md](references/record.md) 维护内部结构。审批前运行只读 `guard` 获取当前 plan / Graph 摘要；批准依据引用外部设计或接口文件时，将稳定文件登记到 record.contracts，使其内容纳入基线。关联真实批准来源；每个任务开始或恢复前用 `guard --task <任务ID>` 校验该任务，交付前运行整体验收校验。`record_valid`、`execution_ready`、`batch_complete`、`delivery_ready` 分别表示记录、所查执行前提、当前批准批次完成和本期整体完成，不把其中任何一个替代业务判断。

合并呈交需求、现状依据、方案、Graph、本期验收方式和执行范围，形成可直接判断“通过 / 需调整 / 不通过”的材料。记录审批人、实际确认来源、时间、批准版本、任务批次和允许操作。

已有明确审批及授权应沿用，不因更换会话或调用 Skill 重复索取。尚未批准时完成材料，停在实施边界并集中提出待确认事项。AI 不代填审批，不把沉默或模板示例当作通过。发布、外部写入、资金与 Git 操作仍按具体用户授权及项目规则执行。

### 5. Loop：执行与验证闭环

本阶段交由 [delivery-run](../delivery-run/SKILL.md)，共用 [execution.md](references/execution.md)。仅处理已批准范围内依赖满足、权限可用的任务，同批次常规步骤连续执行；每项任务实施、验证、诊断、修复、重验后判定，未满足依赖不推进。

区分实现缺陷、测试 / 配置问题、必需环境缺失、业务或范围冲突、体验偏差、越权 / 到限。按原因修复、阻塞、提交决策或停止；外部结果不明先只读核实。保存实际结果、累计消耗与恢复入口。

### 6. Acceptance：整体验收与交付

按批准的本期验收检查完整需求、任务组合、异常、回归和体验。方法可用源码 / 契约审查、构建、测试、本地、Mock、测试服务、浏览器操作或约定复核，结论限定在实际覆盖范围。

本期必需验收与整体验收通过、必要交付材料齐备且有覆盖当前版本的约定接收记录后，可确认“本期研发交付完成”。按 [record.md](references/record.md) 关联接收摘要，不能随重验自动沿用旧接收。已批准列为后续的真实环境专项独立保留 `NOT_VERIFIED`，不自动阻止本期完成。已约定为本期必需的检查不能自行移至后续或记为通过。

### 7. Knowledge：文档与知识沉淀

随决策、实现和检查持续更新运行、接口、交接说明及高价值知识，本阶段汇总。文档知识更新不等待全部真实环境结果。区分设计决策、静态实现、实际运行和未知项；后续实测补证据、复核受影响结论并保留历史。

按 [knowledge.md](references/knowledge.md) 更新已有正文和主题索引，核对文档与实现一致及实际引用，登记原有 handoff.knowledge 状态。批准前规划必要文档范围；批准后进度写 record，不修改批准 plan 的字节。下一需求按需检索和核实形成复用闭环，不强制每需求新增文件。

## 横向约束

- 轻量记录：新需求复用同一 plan.md / record.json。方案和 Graph 的可读审批视图合并在 plan，结构化任务定义、审批、状态与证据只在 record 维护；审批前核对两者一致，不另建任务库。Agent 维护内部编号和摘要，用户负责目标、审批、关键决策与接收。
- 阶段授权：遵守任务、资源和操作边界。连续执行的修复 / 时间 / 费用限制在原审批时集中确认，任务继承；未配置不能推定无限执行。可建议每任务最多三次实质修复，采用前须确认，不替用户填写预算；无有效进展时停止并报告。
- 状态：`PENDING → READY → RUNNING → VERIFYING → DONE`；范围内修复为 `REPAIRING → VERIFYING`；异常退出为 `BLOCKED / NEED_DECISION / STOPPED`。DONE 只覆盖当前任务本期必需验收，整体验收另判。
- 证据与恢复：关联被检查版本 / 对象、方法、条件、预期、实际和位置。恢复核对实际工作区、进程、证据和审批，保留累计限额，不能仅凭上一条总结认定完成。
- 范围变化：业务含义、架构、任务范围 / 依赖、必需验收或风险操作有实质变化，复核受影响部分；任务内步骤细化和独立任务顺序调整按原批准边界处理。

## 交接表达

先说业务结果：完成什么、怎样检查、覆盖哪里；再给成果入口、本期未满足项、后续专项、文档更新与下一步。待审批时集中给具体材料和决定项；待人工验收时给可观察步骤与预期，由 Agent 回填内部记录。

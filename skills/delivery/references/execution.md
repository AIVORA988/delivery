# 执行、验收、知识与恢复

适用：已审批实施、项目内返修、整体验收、中断恢复与后续补验。工具按实际能力接入；这里规定行为，不提供自动调度服务或强制权限系统。

依赖 Guard 的自动实施、返修及正式完成判定需要可用的 Python 3.10+；缺失时保存原记录与恢复条件，按 [setup.md](setup.md) 仅继续允许的调查、方案草稿或知识整理，不绕过校验或自动安装运行时。

## Loop 调度

核对批准方案、Graph、阶段授权、项目规则、实际工作区与剩余资源。外层选可恢复活动任务或下一个 READY 任务，内层闭环当前任务：

新需求在实施前通过 new 保留原始 Git 工作区起点。Guard 的 change_scope 按 [记录契约](record.md) 核对累计实际修改；FAIL / NOT_VERIFIED 先核实原因并处理，不重建起点隐藏差异。NOT_CONFIGURED 的旧记录或非 Git 项目须人工核对已有改动与本次修改，包含暂存、未暂存、未跟踪、删除和重命名；不能将人工核对描述为程序校验通过。该检查不替代每次操作的范围与用户限制核对。原始报告优先放在本需求运行目录；必要交付文档与知识路径纳入批准任务。

所有新需求在每项任务开始 / 恢复前运行 `guard --project <项目> --id <原需求ID> --task <TaskID>`，要求退出 0 且 execution_ready=true，再核对本轮用户限制。无 --task 时的全局结果不授权任意任务；Guard 不代替操作前实际范围核对。Feature 型方案还须同时传 `--features <本轮所选ID...>`；普通执行入口不能绕过 Feature 选择。

Git 起点可用时，将该次完整 Guard JSON 输出保存到本 run 的临时 `scope-before-<TaskID>.json`；它的 scope_checkpoint 绑定真实操作前工作区、当前基线、具体任务和 Feature 选择。每轮实施 / 修复及其验证后、标记 DONE 或推进任务前，用同一任务与选择运行 Guard，并传 `--changes-since .delivery/runs/<原需求ID>/scope-before-<TaskID>.json`，要求退出 0 且 invocation_scope.status=PASS。它核对操作前后实际变化是否属于当前任务 paths；先前其他批次保持未变的合法成果不误报。本轮任务需要修改共享文件、文档或配置时须已有明确路径授权。保留检查点直到该轮核对结束，不用操作后快照覆盖它来隐藏越界；越界时保存现场、核实影响，不自动回滚或补选 Feature。下一轮允许操作前再取得新检查点。旧记录 / 非 Git 无检查点时人工核对，不能声称程序通过；中断丢失检查点时先审查已有差异与未结束动作，不推断历史归属。检查时校验不提供实时拦截或防篡改。

```text
读取有效审批、范围与资源规则
当本批次还有可执行任务：
  选择可恢复任务或下一个依赖满足的任务
  当当前任务仍可继续：
    核对审批、范围、权限、依赖和剩余限额
    根据当前实际状态实现或执行已允许的修复
    执行当前版本适用的本期必需检查
    保存预期、实际、证据、累计消耗与状态，更新相关文档
    若必需检查通过且证据有效：交接并标记 DONE，退出内层
    分类失败：范围内修复 / 缺少必需条件 / 需要决策 / 停止
    若允许修复：先登记尝试，再实施，返回验证与判定
    否则：保存原因、解除条件和下一动作，退出内层
  若触发批次停止条件：结束当前自动运行
进入整体验收，或交接当前状态与下一入口
```

恢复 VERIFYING / REPAIRING 时先核实现状，选择验证或修复；不要因任务不是 READY 而遗漏，也不盲目重复外部写入。命令、进程与被检查产物应对应当前任务。

### Feature 外层与任务内层

delivery-feature-run 直接采用本轮明确的 Feature ID 或唯一可定位的名称，不重复询问；范围缺失或有歧义时，按该入口的“本轮选择”规则，优先原生多选统一提交，否则一次输入全部 ID，完整提交后才校验与执行，首项或临时选择不启动任务，取消 / 未答不执行。所选模块须获完整授权，完整授权后仍遵守本轮指定子任务或单步停止限制。用 --features 校验 selection_ready，依 feature_order 串行推进；所选未完成前置须同选，遗漏不自动补入。当前 Feature 的子任务按上文 Task Loop 执行，完成记录仅写原 record。全部子任务 DONE 后执行 Feature 的 checks 并保存真实证据，模块 complete 后才推进依赖它的 Feature。没有新任务但模块检查未完成时应做已批准模块验收，不把 execution_ready=false 误解为模块验收已通过。

selection_complete 仅代表本轮选择完成，batch_complete 仍代表原批准任务批次完成。阶段交接更新知识和 handoff.resume；下次按本轮指令确定范围，不默默沿用旧选择，也不重复询问已明确范围，保留有效进度与用量。全部本期 Feature 完成后独立执行 overall 的完整链路 / 异常 / 回归与实际接收。共享规则不启动后台调度或真实并行引擎。

### 失败分类和退出

| 原因 | 处理 |
| --- | --- |
| 实现缺陷 | 定位根因，在范围与剩余额度内修复，再验受影响项与必要回归 |
| 测试 / 配置 / 数据错误 | 在授权内修正条件，保留原始失败；不为通过而改掉业务预期 |
| 本期必需环境、能力、权限缺失 | BLOCKED，记录条件、影响和入口，只阻塞相关工作 |
| 业务、范围、架构或验收冲突 | NEED_DECISION，提交问题、影响、建议和受影响部分 |
| 体验偏差 | 按已确认样板和验收修正；新方向或新范围提交复核 |
| 到限、无进展、越权、用户停止 | STOPPED，保存成果与状态 |
| 外部动作结果不明 | 先只读核实，未确认不重放，记录相关 BLOCKED |
| 已批准后续专项暂无条件 | 保持专项未验证，继续本期获授权且独立的工作 |

一次实质修复从允许启动并登记尝试开始，到重验判定结束；启动失败也记录。累计跨会话保留，下一次启动前检查次数限制，已允许的一轮仍受时间、费用、风险限制。外部等待不计代码修复次数。

先登记 repairs 再进入 REPAIRING，并再次核对具体任务 Guard；最后一次已登记修复允许在剩余时间内完成重验，不能把同一计数用于新一轮修复。到时间上限停止新操作，超过任务时间限额的记录不能直接标记 DONE 交付；合法历史 DONE 按其原有效批准限额判断，不用新批次的较低限额追溯否定。

### 状态

| 状态 | 含义 |
| --- | --- |
| PENDING | 前置任务正常未完成 |
| READY | 依赖满足，审批、授权、能力和必需条件具备 |
| RUNNING | 实现或执行中 |
| VERIFYING | 检查当前成果，等待本次判定 |
| REPAIRING | 已允许在范围和额度内修复，完成后回 VERIFYING |
| DONE | 当前任务本期必需验收通过、证据有效、必要交接可用 |
| BLOCKED | 缺少本期必需条件或结果不明 |
| NEED_DECISION | 业务、范围、验收等判断需要确认 |
| STOPPED | 到限、无进展、越权或明确停止，入口已保存 |

对象、验收标准或覆盖行为改变时，复核历史 DONE 和证据。单任务 DONE 不代表整体验收通过。

已完成提供方返修时，先核实运行中命令与外部结果，再沿任务依赖、Feature 依赖和实际接口 / 文件影响定位直接及间接受影响项。一次更新原 record：将需等待前置的 READY / 活动 / DONE 后继回 PENDING，受影响任务、模块及 overall 检查追加当前基线的 NOT_VERIFIED 证据，说明原因，保留原报告与历史证据；独立分支保留。先确认当前有效批准覆盖返修和后继活动，再登记提供方 repairs、进入 REPAIRING 并按具体任务 Guard / 检查点执行；历史审批只证明历史 DONE，不授权新返修。提供方通过后依次恢复后继、模块和整体验收，不能只把旧状态改回 DONE。保留修复和时间用量；单纯重验不计代码修复。范围缺授权或契约 / 定义实质变化回原审批关口，不新增审批层。

分批开发继续原 run、统一设计与模块契约，保持累计消耗。确认依赖完成后将相应 PENDING 任务转 READY，再做具体任务校验；不得为取得放行跳过前置工作。当前批次完成时保存交接，未批准的模块不启动；batch_complete 不代表整体完成。最终集成任务和 overall 检查仍覆盖组合业务、接口匹配、关键异常和必要回归。

发现接口契约变化先分析提供方、消费方及已完成模块的影响，复核受影响设计、任务、审批和证据；不得只更新摘要或沿用历史 DONE。原 Guard 采用整个 plan / Graph 基线，实质变更后即使某模块无影响，也须在复核后为当前基线补充有效检查依据，不能自动复用旧 PASS。

## 证据和整体验收

证据关联需求 / Task / 验收、契约版本、被检查源码 / 配置 / 产物或实例、方法、环境、输入、预期、实际、结果、时间与位置。Agent 维护索引并引用现有报告，不要求用户手填。

检查实际执行、条件明确且结果满足预期时才记 PASS。静态审查、构建、Mock、本地、测试服务、真实运行和人工复核分别限定结论。单项构建、结构校验或测试数量不能替代整体验收。未运行记 NOT_RUN，无法验证记 NOT_VERIFIED，实际失败记 FAIL，并保留原因。

整体验收检查：本期需求到成果与检查的覆盖；任务组合后的完整业务路径；接口、页面、数据与配置匹配；关键异常、权限、空状态和旧路径回归；按约定方法判断体验和可接手性；记录实际接收主体、结论与来源。

对照实际差异与批准任务核对修改范围、调用方和必要回归，subjects 覆盖检查所依赖的实际版本；不能仅引用无关文件证明业务通过。已约定阻断的失败须有当前有效 PASS 解除，不能用对象变化或未运行状态清除。

验收前逐项核对实际变更是否有检查依据；subjects 绑定实现、关键配置和影响结果的必要依赖，公共能力变化检查消费方，不只引用入口文件或报告。无需枚举整个仓库，但授权路径不等于已验证覆盖。模块 / 整体检查若发现必须修改业务文件，先按返修规则恢复相应任务并取得操作前检查点，不借检查名义修改其他 Feature；原始输出优先保存在本 run。

需要人工接收时，用业务语言列出操作、预期和“通过 / 失败 / 暂时无法验证”的反馈方式，由 Agent 回填。项目约定由其他主体接收时按该约定执行，不虚构接收记录。

接收前先确认全部任务合法 DONE、必需任务 / 模块 / 整体验收通过及文档知识交接就绪，再运行 Guard 取得非空 acceptance_sha256；实际接收来源须覆盖该版本，之后才将摘要与接收人、时间和来源关联到 overall.accepted_sha256，并再校验。字段与兼容处理以 [record.md](record.md) 为准。重验或成果变化使旧摘要失效时，先核实实际接收是否覆盖新版本，不因测试通过自动更新接收摘要；无法证明时完成约定接收。Guard 不判断全部语义影响或接收来源真实性。

**本期完成**：批准范围内必需验收、整体验收、必要材料和约定接收记录齐备，可正式确认“本期研发交付完成”。已批准为后续的真实环境专项保持独立 NOT_VERIFIED 和恢复入口，不抹掉本期结果，也不据此声称真实运行通过。

本期必需检查不可行时，提交替代方法和覆盖差异供确认，不自行降级。等待期限由项目约定；到期保存候选材料、未满足项与恢复条件，结束等待，不自动变成 PASS。独立且仍获授权的任务可继续。

## 文档与知识

具体目录、按需读取、增量更新和状态口径以 [knowledge.md](knowledge.md) 为唯一规则源；不强制每个任务或需求新增文档。

需求 / 方案阶段记决定和依据；审批后记版本与批次；实现时更新接口、配置和运行说明；检查时记方法、结果、限制和待验；交付汇总成果、复现入口、接收结论与后续计划。

优先更新已有资料，保留来源、历史条件和新证据影响；区分用户陈述、设计决策、静态实现、实测和未知项。无增量不重复追加，不复制全部日志，不保存密码或密钥。

文档知识更新不等待全部真实环境专项。知识库不可写时保留更新稿、目标位置和待同步状态，必要运行材料须可接手。可选经验提炼 / 外部同步不默认阻止交付，项目明确必需的材料按约处理。

## 中断与后续补验

保存批准版本、状态 / 依赖、实际差异 / 产物、未结束命令、外部结果、证据索引、累计修复与消耗、阻塞 / 决策原因及下一动作。

恢复时核对工作区、版本、进程和外部状态，保护现存未确认改动；按对象变化重验受影响项。保留累计额度，重新计算依赖和范围。记录与实际冲突先核实，不凭上一条总结跳到完成。

多执行者明确唯一记录写入方，或复用已有锁与版本检查。写前重读，避免覆盖并发更新。后续真实结果补入专项、证据和文档；发现缺陷关联原任务并复核受影响结论，保留原检查时间与范围。
